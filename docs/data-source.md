Дата проверки: 18 октября 2026 года. Этап 1 выполнен: основные сценарии проверены реальными HTTP-запросами без API-ключа. Проверка подтверждает доступность на эту дату, а не SLA и не полноту всех профилей.

Источники: [OpenAPI](https://api.deadlock-api.com/openapi.json), [документация](https://api.deadlock-api.com/docs), [репозиторий поставщика](https://github.com/deadlock-api/deadlock-api), [лицензия кода](https://github.com/deadlock-api/deadlock-api/blob/master/LICENSE). ## Поля и использование

| Наш показатель | Endpoint / поле | Нормализация и ограничения |
| --- | --- | --- |
| Поиск | players/steam-search: account_id, personaname | search_query обязателен; показывать кандидатов, имя не уникально |
| Профиль | players/steam: account_ids, personaname, avatarfull, last_updated | ID64 и account ID принимаются; friends/realname/countrycode не сохраняем |
| История | players/{id}/match-history | Возвращает массив целиком; upstream cursor/limit отсутствуют |
| Начало/длительность | start_time, match_duration_s | Unix seconds / seconds; UTC в нашем API |
| K/D/A | player_kills, player_deaths, player_assists | Суммировать по выбранным загруженным записям |
| Победа игрока | player_match_outcome | 1=win, 2=loss; 0/3/4/5 исключить из знаменателя winrate, сохранить исходный код |
| Души | net_worth | Показывать как net worth на конец игры, не как доход за всё время |
| Ранг | rank: badge/rank/subrank/last_match | badge=0 и last_match=null → публичный rank=null; средний ранг команды не подменяет личный |
| История ранга | ranked_display_badge, ranked_delta | Может отсутствовать; delta — прогресс ранга, не наша оценка MMR |
| Матч | metadata.match_info | Динамический объект в OpenAPI: нужны fixtures и терпимость к дополнительным полям |
| Победившая команда | match_info.winning_team | Не путать с player_match_outcome; сохранять match_outcome/not_scored |
| Урон | players[].stats[].player_damage | Последний доступный snapshot по time_stamp_s; при отсутствии null, не сумма snapshots |
| Предметы | players[].items[] | Это история приобретений с game_time_s/sold_time_s/flags, не готовый итоговый инвентарь |
| Герои | assets/heroes: id/name/class_name | only_active=true, language=russian; версия справочника должна фиксироваться при загрузке |
| Глобальный winrate | analytics/hero-stats: wins/losses/matches | wins/(wins+losses), null при пустом знаменателе |
| Популярность | analytics/hero-stats: matches | Первая версия: количество игр и сортировка; процент выбора пока не выводить |
| Противостояния | hero-counter-stats: hero_id/enemy_hero_id/wins/matches_played | same_lane_filter=true по умолчанию; называть «на одной линии» |
| Сборки | hero-build-stats: hero_build_id/wins/losses/matches/players | Первая выбранная сборка в начале матча; не доказательство её использования всю игру |

`matches_per_bucket` в проверенном ответе равно matches соответствующего героя; нельзя использовать его как общий знаменатель pick rate. Для процента выбора понадобится отдельно подтвердить общее число матчей при точно совпадающих фильтрах. До этого отображаем количество игр.

Содержимое сборок и справочник предметов в этом этапе не запрашивались. Страница героя может показывать статистику сборок; подробный состав потребует проверки соответствующего endpoint перед подключением. Покупки матча показываем хронологией; итоговый инвентарь не реконструируем без проверки flags/upgrade semantics.

## История и предел загрузки

Пагинацию предоставляем из PostgreSQL. Адаптер upstream возвращает `list[ProviderHistoryEntry]`, а не выдуманный ProviderMatchPage с курсором.

Первое обновление: сохранять до 100 последних записей истории после сортировки `(start_time, match_id)`; получать metadata только для 20 последних, которых ещё нет локально. Метаданные других сохранённых игр подгружать отдельным заданием по открытию матча, с deduplication. Пока нет деталей, показывать историю и статус partial. Ограничить размер HTTP-ответа истории 10 MiB и timeout 20 секунд; превышение — контролируемая ошибка, без частичного разбора JSON.

Первый endpoint истории всё равно возвращает полный upstream-массив: наш лимит уменьшает хранение и число последующих запросов, но не объём upstream-ответа. coverage=partial при отсечении до 100 записей, иначе unknown: даже 4 полученные игры не означают полную историю.

По документации полная/свежая история через Steam зависит от дружбы с ботом поставщика; обычный пользователь получает сохранённые записи ClickHouse. `force_refetch=true` не включать автоматически. При 429 history может содержать пригодный массив fallback-данных: адаптер должен проверить тело и сохранить его как устаревшее, а не повторять запрос вслепую.

## Лимиты и доступ

Проверенные запросы работали без ключа. OpenAPI поддерживает `X-API-KEY` и query api_key; в нашем приложении использовать только заголовок из серверного окружения.

| Группа | Документированная квота без ключа |
| --- | --- |
| Поиск / чтение Steam-профиля | 100 запросов/с на IP |
| Принудительный refresh профиля | 3/мин + 15/час на IP |
| История (обычное чтение) | 100/с; для друзей бота дополнительно 10/час |
| force_refetch истории | 1/час |
| metadata cache / S3 / Steam fallback | 100/с / 100 за 10 секунд / 3 в час |
| Все analytics вместе | 200/мин на IP; с ключом 400/мин; общий лимит 2000/мин |
| Ранги / assets | На конкретных проверенных операциях квота явно не указана; отсутствие квоты не означает безлимит |

Стартовая политика приложения: общий внешний лимит 1 запрос/с, concurrency=1, плюс endpoint buckets; history не чаще 1 раза в 6 минут на IP без ключа, чтобы учитывать потенциальную bot-friend квоту. Более частый refresh возвращает сохранённые данные или queued с отложенным временем запуска. Для высокой нагрузки понадобятся ключ и уточнение квот. Metadata — disable_steam=true; автоматический Steam fallback выключен. Внешние квоты и публичные лимиты нашего API — разные ограничения.

503 может приходить без Retry-After, как в реальном запросе. При наличии заголовка соблюдать его, иначе использовать 5/15/45 секунд и максимум три повтора. Не удалось воспроизвести 429 без искусственной нагрузки — такой случай покрывается синтетическим тестом на этапе 3, а не выдаётся за реальную фикстуру.

## Идентификаторы, фильтры и непроверенные края

- Для стандартного публичного individual Steam ID64: account_id = steam_id64 - 76561197960265728. Проверено равенство возвращённого account ID и преобразования для одного реального профиля. Нулевые ID не отправлять; валидировать universe/type/instance, хранить положительный uint32 account ID в BIGINT, наружу отдавать строкой.
- OpenAPI описывает account ID как int32 с minimum=0, но не следует ограничивать все Steam account ID знаковым int32 без проверки. Граничные uint32 на живом API не тестировались.
- Search по умолчанию требует 5 матчей за 30 дней. Наш поиск явно передаёт min_matches_played_last_30d=0, чтобы не скрывать малоактивных пользователей. Это всё равно поиск по базе поставщика, а не гарантия полного Steam-каталога.
- Аналитика поддерживает временные и min/max_average_badge фильтры. Последние относятся к среднему рангу обеих команд; UI должен говорить «средний ранг матча».
- Семантика включительности верхней временной границы upstream не установлена по одному ответу. Перед реализацией фильтров аналитики проверить исходный код запроса или граничную фикстуру; наш контракт [from,to) остаётся неизменным.
- Числовые game_mode/match_mode сохранять как raw codes до проверки enum. Не сопоставлять режимы по догадке.
- Настоящий partial metadata ответ не найден: наблюдались полноценный матч и 503. Тест неполных полей на этапе 3 должен быть явно синтетическим, производным от сохранённой фикстуры.

## Решение по первому релизу

Поиск → профиль → история → матч реализуемы. Основная статистика героев, сборок и противостояний также доступна. Корректировки: upstream history без пагинации, частичная загрузка деталей, неизвестный ранг как null, популярность числом игр, покупки как хронология. Живая игра, процент pick rate и итоговый инвентарь не обещаются на основании этого этапа.
